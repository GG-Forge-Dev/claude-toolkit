# Datos que se crean, editan o borran
- Lo que no puede repetirse o romperse (nombres únicos, una reserva por mesa, saldo ≥ 0, que no quede algo huérfano) se garantiza **en la base de datos**: índice único, FK, CHECK o transacción. Comprobarlo antes en el código no basta, porque dos peticiones simultáneas pasan las dos la comprobación. La UI (deshabilitar el botón) solo ayuda.
- Cada endpoint o acción que **crea, edita o borra** lleva sus tests, incluido el de duplicado y el de dos peticiones a la vez. Al tocar uno, usa la skill `escrituras`.
- Después de guardar, cada dato se recarga **una sola vez**. Si hay tiempo real (SSE, WebSocket, Supabase Realtime…) que avisa el cambio a todos los dispositivos, el que guardó no recarga además por su cuenta: espera ese aviso y recarga solo si no llega. Al probar una acción, mira la pestaña Network: ninguna consulta se pide dos veces.
- **Búsquedas al escribir: una petición al dejar de escribir, no una por letra.** Toda consulta al servidor que depende de lo que se teclea (buscar clientes, sugerencias, filtros con servidor) pasa por un debounce de ~300 ms, hecho **una sola vez** en el producto (un hook como `useDebouncedValue`) y aplicado dentro del hook de datos, para que ninguna pantalla lo olvide. Se prueba escribiendo letra por letra y contando las peticiones.
- **Doble clic: una acción, una vez.** Todo control que escribe (guardar, cobrar, enviar, aceptar, borrar, generar) queda deshabilitado mientras su petición está en curso (`disabled={mutation.isPending}` o un estado puesto **antes** del `await`), y la protección real está en el servidor (único, idempotencia). Se prueba con un doble clic en el E2E: sale un solo POST.
- Los tests no dan por hecho qué datos hay: cada test crea los suyos con nombres únicos y los busca por id. Si un test falla «a veces», antes de arreglar el test busca el fallo real en la app.
